Architecture

Core owns coordination. Containers run turns.

Suzumio separates orchestration from execution. The core process owns project truth and scheduling; the Docker runner performs one isolated turn and exits.

Core Process

The core process is the authority for every project-level record. If data should be visible in CLI, HTTP, or WebUI, it belongs in SQLite through the core store.

Runner Contract

The runner is deliberately narrow. It receives all context through one input file and reports back through one output file.

type RunnerTurnInput = {
  project: string
  agent: { id: string; role: string; prompt: string; model?: string }
  turn: { id: string; prompt: string }
  workspace: string
  controllerUrl: string
  token: string
  runner: RunnerConfig
  tools: ToolDefinition[]
}
type RunnerTurnOutput = {
  text: string
  usage?: Record<string, unknown>
}

This contract keeps the runner replaceable. The current runner can be evolved or replaced without changing project state semantics.

Docker Isolation

The first backend is Docker-first. Each turn container receives:

  • A bind mount for /turn containing input and output files.
  • A bind mount for the agent workspace at /workspace.
  • Environment variables for project id, agent id, turn id, token, and model provider API key environment variables.
  • host.docker.internal mapping so the runner can call the Suzumio ToolHost.

The current implementation keeps completed containers until they are removed by the operator. This is useful for debugging early runs and should later become configurable.

Tool Flow

Model asks for tool
  runner converts AI SDK tool call
  runner POSTs /tool to Suzumio
  ToolHost verifies token and tool allowlist
  ToolHost records tool_calls row
  core tool runs against SQLite/artifact store
  ToolHost records success or failure
  runner returns tool output to model

The model never receives arbitrary host tools from Suzumio by default. Tools are configured per agent and executed by the core ToolHost.

Message Delivery

Agents do not call read_messages. Suzumio renders unread inbound messages into the next turn prompt. This avoids polling loops and gives the scheduler a precise record of which messages were consumed by which turn.

SQLite as Project Truth

Each project has one SQLite file. The container runner does not maintain the project database. It may keep temporary local execution state inside the container, but durable state must flow through output files or ToolHost calls.

Why Not Reuse Chatbox Directly?

The previous chatbox code contained useful ideas: model presets, AI SDK integration, tool conversion, and context handling. But it also owned a session store and built-in host tools. Suzumio intentionally moves project state, tools, and permissions into the core runtime. The runner can borrow implementation ideas without inheriting those boundaries.
